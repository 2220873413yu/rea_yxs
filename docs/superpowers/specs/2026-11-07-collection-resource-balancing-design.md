# 普通采集资源均衡分配

用户已确认：资源目标比例为粮、木、铁 1:1:1，按当前存量加已派队伍预计收益排序；同类队伍限制分散采集，手动队伍也计入。不增加固定轮询，不改联盟采集的独立开关或调度。

## 数据和分配

- 原生 `SLGMainModel:getMySLGResource()` / `TUserResource` 的前三个字段分别为粮、木、铁。读取当前登录地图中的存量，不包含背包未使用资源包。
- 本方行动列表按队伍 ID 去重，不以助手记录的出征为准。普通采集行军、采集中队伍计入同类数量；返城队伍不占同类限制，但已携带资源仍计入预计入库。已经返回的队伍不重复计入。
- `TArmyInfo.vecItem` 中 70001、70002、70003 分别为已携带粮、木、铁。其他战利品不计入资源。
- 普通采集中的任务详情含 `TSLGResourceCollectInfo.iCount/iMax`；优先使用对应队伍的服务端上限估算最终收益，结合实时余量封顶。行军中尚无驻留记录时，使用目标选将响应中的该英雄负重和实时余量估算。以上仅用于分配，不用于计算采集/返城时间。
- 预计收益替代同一支队伍的已携带数量，不双重相加。其他行动（包括联盟采集返城）已携带的已知资源也计入；不会为普通采集额外触发联盟查询。
- 对清单中每类资源按 `当前存量 + 预计入库` 从少到多排序；相同值优先当前该类队伍更少，再按资源点距离、坐标稳定排序。同类仍优先近点。
- 同类上限为 `max(1, ceil(服务器普通采集队伍上限 / 2))`：2 队上限时同类最多 1 队，3～4 队时同类最多 2 队。只限制助手新增派出，不撤回已有人工队伍。
- 类型达到上限时跳过；没有其他合格点则等待现有通知/阶段时间或手动检查，不突破上限填满队伍。

## 生命周期和安全

只在现有检查已确认有空闲队伍、准备规划目标时读取存量和收益。每个当前行动目标本次最多查询一次；需要时复用既有资源/选将查询及新鲜英雄/行动确认，不增加定时服务器请求。查询后重新核对行动列表、队伍上限，避免队伍回城导致收益重复计算。无法确认仍在行动队伍的资源类型时，本次等待，不按零成本继续派队。

保持按清单加载区域、同盟空位、实时余量（4级以上至少4万）、本方目标去重、最佳英雄及共用恢复逻辑。一次仅派一队，确认响应后下次检查重新分配。开关默认关闭，关闭后不再发起后续查询或出征；实际出征和道具消费的验收使用隔离测试。

助手显示粮木铁的当前存量、预计入库、各类在采/行军数量与同类上限；显示等待类型上限或未知收益的原因，所有预计数明确标为预计。

## 验证

覆盖存量优先于距离、在途收益改变优先级、同类上限、手动队伍、返城及入库去重、联盟返城携带、相同存量稳定排序、未分类队伍等待、出征逐队重新决策、停止取消以及等待期间没有固定查询。执行生产 Lua 的字段适配测试和服务调度测试，并只读验证当前模拟器存量/收益。
