# 自动补满步兵：第一版设计

## 已确认目标

在这台电脑的雷电模拟器中运行《英雄杀》。用户打开“自动造步兵”开关后，游戏保持当前地图或战斗界面，不进入兵营，自动训练步兵并使用紫色五分钟训练加速，直到步兵实际数量达到当前上限。用户关闭开关后不再发出新的消耗型请求。

## 第一版形态和选择

采用电脑上的小控制窗口，只有“自动造步兵”开关，以及当前状态、步兵数量/上限、道具数量和停止原因。它连接当前模拟器的游戏进程，复用游戏自己的 Lua 业务调用和当前登录会话。

这延续已讨论的“外部控制面板＋游戏进程内模块”路线。相比独立重写协议，能够复用会话、消息加密和响应处理；相比修改 APK，不需要重新签名或覆盖安装。第一版依赖电脑、ADB、模拟器现有 root 和运行中的游戏，不是脱离电脑的手机安装包。

## 接入验证先于自动循环

先验证模拟器的 ARM64 翻译环境是否支持进程接入。首次接入只读取模块、Lua 状态和业务函数，不发送训练、加速请求。接入失败、游戏退出或地址不匹配时停止并明确报错，不自动重启或修改游戏。

能接入后，定位并读取兵营模型中的当前步兵数量、在训数量、可训练上限和道具库存，核对字段语义。不能可靠读取这些状态时，开关保持不可用；不能只用截图中的固定上限或日志里的旧值代替。

最后才验证保持地图界面时的一次训练与一次加速。训练协议 11029、兵种 411、加速协议 186、道具 70251 仅作为已知样本；实际调用优先使用游戏业务函数，禁止盲目重放含身份上下文的旧包。

## 循环规则

1. 开关默认关闭，启动程序不自动消耗资源。
2. 打开后读取当前真实状态，确认角色、地图、游戏版本及步兵上限可用。
3. 步兵数量已经达到上限则自动关闭；已有训练任务要先计入，避免超过可训练容量。
4. 每次只发起一个训练或加速命令，收到成功响应并核对新状态后再继续。
5. 只使用紫色五分钟训练加速 70251，不使用通用加速、元宝或其他道具。
6. 为完成“直接造满”，即使剩余不足五分钟，也允许使用一个五分钟道具完成本轮，因此会存在剩余时长浪费。状态或队列关系未确定时停止，不能猜测加速作用范围。
7. 资源不足、道具耗尽、服务器拒绝、断线或无法确定请求结果时关闭开关并显示原因。消耗型请求超时后先核对状态，不直接重发。
8. 关闭开关后不再发送新请求；已经被服务器接受的训练不会取消或回滚。
9. 每次运行限制训练、加速请求总量；限制按已核实的目标差额和当前队列计算，防止状态异常引起无限消耗。

## 组件

- 控制窗口：用户开关和可见状态，不处理游戏协议细节。
- 控制器：串行状态机、停止条件、超时核对和本地日志。
- 进程桥：在游戏主线程读取模型及调用业务函数，桥断开后不留自主循环。

## 验收

- 地图界面保持可见，不自动打开兵营。
- 关闭开关时不发送训练或加速请求。
- 单步验证中服务器响应成功，兵营状态实际变化。
- 开启后持续补兵，在真实上限停止，不多造或无限加速。
- 仅扣除预期的训练资源和指定加速道具。
- 断线、异常、关闭窗口均停止后续请求；可从日志核对每次命令及结果。

## 验证边界

当前已确认正常 UI 操作的训练、加速协议及效果，尚未验证进程桥和后台调用。本设计不把它们视为已经实现。进程接入失败时交付明确诊断和可复核结果，不交付只有空开关的伪实现。
